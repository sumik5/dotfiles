# GitLab Merge Request 生成コマンド

このコマンドは、現在のブランチと分岐元ブランチとの差分を分析し、GitLab Merge Request用の説明文を自動生成します。

## 使用方法

```bash
/generate-mr [JIRAチケット名]
```

### 引数

- `[JIRAチケット名]`: オプション。JIRAチケット名を指定するとMRタイトルの先頭に追加されます
  - 例: `/generate-mr PROJ-123`, `/generate-mr ABC-456`

### 使用例

```bash
# JIRAチケットなし
/generate-mr

# JIRAチケットあり
/generate-mr PROJ-123
```

## 実行手順

### ステップ0: Gitリポジトリの確認

まず、現在のディレクトリがGitリポジトリであることを確認してください：

```bash
git rev-parse --is-inside-work-tree 2>/dev/null
```

失敗した場合: "エラー: Gitリポジトリではありません" を表示して終了

### ステップ1: ブランチ情報の取得と分岐元ブランチの特定

```bash
# 現在のブランチ名を取得
CURRENT_BRANCH=$(git branch --show-current)

echo "現在のブランチ: $CURRENT_BRANCH"
```

分岐元ブランチを特定するため、以下の手順で調査してください：

```bash
# 1. リモート追跡ブランチの確認
git branch -vv

# 2. 主要ブランチ（main, master, develop等）との分岐点を確認
# 各ブランチとの共通祖先からのコミット数を比較
for branch in main master develop; do
  if git show-ref --verify --quiet refs/heads/$branch 2>/dev/null || \
     git show-ref --verify --quiet refs/remotes/origin/$branch 2>/dev/null; then
    MERGE_BASE=$(git merge-base HEAD $branch 2>/dev/null || git merge-base HEAD origin/$branch 2>/dev/null)
    if [ -n "$MERGE_BASE" ]; then
      COMMIT_COUNT=$(git rev-list --count $MERGE_BASE..HEAD)
      echo "$branch: 分岐点から $COMMIT_COUNT コミット"
    fi
  fi
done

# 3. reflogから分岐元を推測（ブランチ作成時のログ）
git reflog show $CURRENT_BRANCH --format="%gs" | head -5
```

上記の情報から分岐元ブランチを特定し、`BASE_BRANCH` として使用してください。
特定のルール:
- 共通祖先からのコミット数が最も少ないブランチを分岐元とする
- reflogに "branch: Created from" の情報があればそれを優先
- 特定できない場合は main または master をフォールバックとする

```bash
# 分岐元ブランチを設定（上記調査結果から決定）
BASE_BRANCH="<特定された分岐元ブランチ>"

echo "分岐元ブランチ: $BASE_BRANCH"
```

エラー条件:
- 現在のブランチが分岐元ブランチと同じ場合: "エラー: 分岐元ブランチからはMerge Requestを作成できません"
- 分岐元ブランチとの差分がない場合: "エラー: 分岐元ブランチとの差分がありません"

### ステップ2: 変更情報の収集

ステップ1で特定した `BASE_BRANCH` を使用して、以下のコマンドで情報を収集してください：

```bash
# コミット履歴を取得
echo "=== コミット履歴 ==="
git log --oneline ${BASE_BRANCH}..HEAD

# 詳細なコミットメッセージを取得
echo ""
echo "=== 詳細なコミットメッセージ ==="
git log ${BASE_BRANCH}..HEAD --pretty=format:"%s%n%b" --reverse

# 変更統計
echo ""
echo "=== 変更統計 ==="
git diff --stat ${BASE_BRANCH}..HEAD

# 変更ファイル一覧（A: 追加, M: 変更, D: 削除）
echo ""
echo "=== 変更ファイル一覧 ==="
git diff --name-status ${BASE_BRANCH}..HEAD

# 実際のdiff（コード変更の詳細把握用）
echo ""
echo "=== コード変更の詳細 ==="
git diff ${BASE_BRANCH}..HEAD
```

### ステップ3: Merge Request文章の生成

収集した情報を分析し、以下のフォーマットでMerge Request文章を生成してください。

#### 情報の優先順位

MR文章を生成する際、以下の優先順位で情報を活用してください：

1. コミットメッセージ（最重要）
   - コミットメッセージには開発者の意図が凝縮されている
   - 特にConventional Commits形式（feat:, fix:, refactor:等）の場合、変更の種類が明確
   - コミット本文（body）に「なぜ」の情報が含まれていることが多い

2. コード差分
   - コミットメッセージで説明されていない技術的詳細を補完
   - 実際に何が変更されたかの事実確認

3. 変更統計・ファイル一覧
   - 変更の規模感の把握
   - 詳細セクションでのファイル列挙

#### コミットメッセージの活用方法

複数コミットがある場合:
- 各コミットメッセージの要点を統合してMR全体の概要を構成
- 関連する変更はグループ化して説明
- コミット順序から作業の流れを把握し、論理的な説明順序に整理

Conventional Commits形式の場合:
- `feat:` → 新機能追加として概要に反映
- `fix:` → バグ修正として概要に反映
- `refactor:` → リファクタリングとして概要に反映
- `docs:` → ドキュメント更新として概要に反映
- スコープ（例: `feat(auth):`）から影響範囲を把握

コミット本文の活用:
- 「Why」（なぜこの変更が必要か）→ 背景セクションに反映
- 「What」（何を変更したか）→ 変更内容セクションに反映
- 「How」（どのように実装したか）→ 詳細セクションに反映

#### 生成ルール

1. JIRAチケット名が引数として渡された場合（$ARGUMENTS に格納）:
   - タイトル先頭に `[チケット名] ` を付与
   - 例: `[PROJ-123] ユーザー認証機能の実装`

2. タイトルは変更内容を端的に表す日本語で記述
   - コミットメッセージのサブジェクト（1行目）を参考にする
   - 複数コミットの場合は全体を包括するタイトルにする

3. 本文は以下の構成で生成:

```
## 概要

このMRで実現することを1-3文で記述。
何が達成されるのかをユーザー視点で説明。
（※コミットメッセージのサブジェクトから主要な変更内容を抽出）

## 背景

なぜこのMRが必要かを説明。
- 課題や要件があれば記述
- 関連するチケットやドキュメントがあれば記載
（※コミット本文の「Why」部分から抽出。記載がない場合はコード変更から推測）

## 変更内容

このMRで何を実装したかをざっくり説明。
（※コミットメッセージの「What」部分を統合）

主な変更点:
- 変更点1（※各コミットの主要な変更を箇条書き）
- 変更点2
- 変更点3

<details>
<summary>詳細な変更内容</summary>

ファイル単位または機能単位での詳細な変更内容を記述。
技術的な詳細はここに記載。
（※コード差分から技術的な実装詳細を補完）

</details>

## テスト
（※テストコードが追加・変更された場合のみこのセクションを含める）

追加・変更したテストの概要を説明。

テスト内容:
- テストケース1の説明
- テストケース2の説明
- テストケース3の説明

（※テストコードがない場合はこのセクションを省略）

## 動作確認結果

ここに動作確認結果を入れる
```

#### テストセクションの生成ルール

テストコードの検出:
- 変更ファイル一覧から以下のパターンを検出:
  - `*.test.ts`, `*.test.js`, `*.spec.ts`, `*.spec.js`
  - `*_test.py`, `test_*.py`
  - `*_test.go`
  - `__tests__/` ディレクトリ配下のファイル
  - `tests/`, `test/` ディレクトリ配下のファイル

テストセクションの記載内容:
- テストファイルが追加・変更された場合のみセクションを含める
- テストコードの差分から、どのような観点でテストしているかを説明
- テストケース名（describe/it/test関数名）を参考に内容を要約
- 単体テスト、統合テスト、E2Eテスト等の種別があれば明記

テストがない場合:
- テストセクション自体を省略（「テストなし」とは書かない）

#### 動作確認結果セクションの生成ルール

- このセクションは常に本文の最後に追加する
- 内容は「ここに動作確認結果を入れる」というプレースホルダーのみ
- ユーザーが手動で動作確認結果を記入するためのセクション

#### 文章生成の注意点

コミットメッセージの活用:
- コミットメッセージの内容を最大限活用し、開発者の意図を正確に伝える
- コミットメッセージが英語の場合は日本語に翻訳して反映
- コミット本文が空の場合はコード差分から意図を推測して補完
- 複数コミットの場合、重複する説明は統合して簡潔にまとめる

フォーマット:
- Markdownの強調（**太字**、*斜体*）は使用しない
- 項目名はh2（##）から始め、改行して本文を書く
- GitLabのURLはそのまま埋め込む（GitLab viewerが装飾してくれる）
- GitLab以外のURLは `[タイトル](URL)` 形式で埋め込む
- 人間に読みやすく、編集しやすいよう適度に改行と箇条書きを使う
- Human Readableな自然な日本語で記述

### ステップ4: 出力

生成したMerge Request文章をコードブロックで出力してください：

```
=== Merge Request 文章 ===

タイトル:
```
[生成されたタイトル]
```

本文:
```
[生成された本文]
```

===
```

注意事項:
- 前置きの説明やコメントは不要です
- MR文章のみをそのまま出力してください
- 出力後、ユーザーがコピーしてGitLabに貼り付けられる形式にしてください
- タイトルと本文は別々のコードブロックで出力（コピーしやすくするため）
